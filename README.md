# منصة لجنة المسؤولية المجتمعية · سنكري القابضة

> **جلسة جديدة؟** هذا المستودع هو منصة اللجنة:
> - خادم Node بلا إطار عمل (`server.js`).
> - واجهة صفحة واحدة (`index.html` + `js/app.js` + `css/style.css`).
> - قاعدة **PostgreSQL** على الخادم الخاص، وجداولها تُبنى بـ**ترحيلات SQL مرقّمة** (`migrations/`).
> - النشر آلي (CI/CD) عند كل رفع إلى المستودع، ويديره الفريق التقني.
>
> اقرأ هذا الملف كاملاً قبل أي تعديل، وخاصة القسم 4 (الترحيلات) والقسم 8 (قواعد العمل).
>
> **قواعد ثابتة:**
> - شغّل `npm run check` قبل كل رفع.
> - أي تغيير في القاعدة يكون **ملف ترحيل جديد**، ولا يُعدَّل ملف ترحيل طُبّق سابقاً.
> - ارفع رقم `?v=N` في `index.html` عند أي تغيير في `js/app.js` أو `css/style.css`.
> - كل تسليم حزمة جديدة برقم تالٍ.
> - حدّث هذا الملف و«سجل الإصدارات» (القسم 10) مع كل تغيير.

## 2. متغيرات البيئة

| المتغير | إلزامي؟ | الوصف |
|---|---|---|
| `DATABASE_URL` | **نعم في الإنتاج** | `postgresql://user:pass@host:5432/dbname`. التشفير يحدّده `sslmode` في الرابط (انظر الملاحظة). |
| `SESSION_SECRET` | **نعم** | نص عشوائي طويل (40 حرفاً أو أكثر). بدونه يخرج الجميع من حساباتهم مع كل إعادة تشغيل. ثبّته ولا تغيّره مع كل نشر. |
| `PORT` | حسب الخادم | الافتراضي 10000 |
| `MIGRATE_ON_START` | اختياري | الافتراضي: الخادم يطبّق الترحيلات بنفسه عند التشغيل. اضبطه `false` إذا كان خط النشر يشغّل `npm run migrate` كخطوة مستقلة. عندها يرفض الخادم البدء إذا بقي ترحيل ناقص. |
| `PG_POOL_MAX` | اختياري | أقصى عدد اتصالات بالقاعدة (الافتراضي 3، ويكفي) |
| `NODE_ENV` | اختياري | `production` يُظهر تحذيراً إذا شُغّل الخادم بلا `DATABASE_URL` |
| `DATA_DIR` | للتطوير فقط | مجلد تخزين الملف حين لا يوجد `DATABASE_URL` |
| `VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY` | اختياري | مفاتيح إشعارات الجهاز. بدونها يولّدها الخادم مرة واحدة ويحفظها في `csr_kv`. **لا تغيّرها** بعد التشغيل، فتغييرها يُبطل اشتراكات كل الأجهزة. |
| `VAPID_SUBJECT` | اختياري | الافتراضي `https://csr.sankariportal.com` |
| `APP_TZ` | اختياري | المنطقة الزمنية لنصوص التذكيرات (الافتراضي `Asia/Damascus`) |
| `TICK_MS` | اختياري | فاصل مؤقّت الاجتماعات (الافتراضي 60000 = دقيقة) |

**ملاحظة عن SSL:**
- قاعدة على الخادم نفسه أو في شبكة داخلية: الرابط بلا `sslmode` يعني بلا تشفير.
- قاعدة خارجية بشهادة موثوقة: أضف `?sslmode=require`.
- قاعدة بشهادة ذاتية التوقيع: أضف `?sslmode=require&uselibpqcompat=true` (يشفّر دون التحقق من الشهادة).

## 4. القاعدة وترحيلات SQL

### 4-أ. الجداول (بعد 002)
| الجدول | المحتوى |
|---|---|
| `schema_migrations` | `version` · `name` · `checksum` (sha256) · `applied_at`. يديره `db/migrate.js`. |
| `csr_store` | صف واحد `id='main'`: ‏`rev` (يزيد مع كل حفظ) + `doc` من نوع JSONB، وهو المستند **بلا** الحسابات (المشاريع والأحداث والميثاق…) |
| `csr_users` | حساب لكل صف: `id` · `ord` (الترتيب) · `login` · `name` · `role` · `admin` · `must` · `pw` (تجزئة scrypt) · `extra` (JSONB لبقية الحقول) |
| `csr_backup` | صف لكل يوم (`day`): المستند **كاملاً مع الحسابات**. يُكتب مرة كل ساعة على الأكثر، ويُحذف ما مضى عليه أكثر من 30 يوماً. |

### 4-ب. الأوامر
```
npm run migrate:status     عرض المطبَّق والناقص (لا يغيّر شيئاً)
npm run migrate            تطبيق الناقص بالترتيب
```
تقرأ هذه الأوامر `DATABASE_URL` من البيئة.

### 4-ج. كتابة ترحيل جديد
1. أنشئ `migrations/003_وصف_قصير.sql`. الاسم أرقام ثم `_` ثم أحرف إنكليزية أو أرقام أو `-`. الرقم أكبر من آخر رقم.
2. اكتب SQL عادياً. المشغّل يضع الملف كله في معاملة، فلا تكتب `BEGIN` ولا `COMMIT`.
3. **لا تعدّل ملفاً طُبّق.** يحسب المشغّل بصمة كل ملف، ويرفض العمل إذا تغيّر ملف قديم. التصحيح يكون بملف جديد.
4. أي حقل جديد في المستند (JSON) **لا يحتاج ترحيلاً**. الترحيل للجداول والأعمدة والفهارس، أو لنقل بيانات.
5. إن غيّرت شكل `csr_store` أو `csr_users`، فحدّث `db/store-pg.js` (`readAll` · `writeAll` · `userRow` · `rowUser`) في الرفع نفسه.
6. أضف فحصاً في `tools/smoke.js` ثم `npm run check`.

## 5. النشر (CI/CD): ما يحتاجه خط النشر

الفريق التقني يبني خط النشر. المطلوب منه فقط:
```
npm ci --omit=dev          # الاعتمادية الوحيدة في الإنتاج: pg
npm run migrate            # اختياري: الخادم يطبّقها بنفسه عند التشغيل إن لم يُضبط MIGRATE_ON_START=false
<إعادة تشغيل الخدمة>       # node server.js بمدير العمليات (pm2 · systemd · Passenger…)
```
- **فحص الصحة:** `GET /healthz` ← `{"ok":true}`. وفي السجل `storage: postgres · schema 002`.
- **الفحص قبل النشر (في CI):** `npm ci` ثم `npm run check`. يحتاج devDependencies، ولا يحتاج قاعدة حقيقية.
- **نسخة واحدة فقط من الخادم.** البيانات تُحمَّل في ذاكرة العملية، فلا cluster ولا أكثر من instance.
- **قبل كل ترحيل مهم:** خذ نسخة بـ`npm run db:export` (القسم 7).
- **إن كان أمامه nginx:** اجعل `client_max_body_size` ‏25m على الأقل، لأن المستند يُرسَل كاملاً مع صور المشاريع. الضغط والـETag يصدران من الخادم نفسه.
- **المنصة تعمل من جذر نطاق** (مثل `csr.example.com`)، لا تحت مجلد فرعي.

## 6. الانتقال من تخزين الملف إلى PostgreSQL (مرة واحدة)

**المصدر:** الملف `data/store.json` **الموجود الآن على الخادم**، ففيه كل ما أُدخل منذ النقل من Neon.

1. أنشئ قاعدة ومستخدماً في PostgreSQL على الخادم:
   `CREATE DATABASE csr; CREATE USER csr WITH PASSWORD '...'; GRANT ALL ON DATABASE csr TO csr;`
   وفي PostgreSQL 15 أو أحدث أضف أيضاً: `ALTER DATABASE csr OWNER TO csr;`
2. **أوقف خدمة المنصة**، حتى لا يُكتب شيء جديد في الملف أثناء النقل.
3. انسخ الملف جانباً احتياطاً: `cp data/store.json ~/store-before-pg.json`
4. من مجلد المشروع، وبعد نشر هذه الحزمة و`npm ci`:
   ```
   DATABASE_URL="postgresql://csr:...@localhost:5432/csr" npm run db:import -- ~/store-before-pg.json
   ```
   - يطبّق الترحيلات ثم يكتب البيانات، ويطبع: `OK: schema 002 · rev … · 9 users · … projects`.
   - إن وُجد مجلد `backups/` بجانب الملف تُستورد نسخه اليومية أيضاً.
   - يرفض الكتابة فوق قاعدة فيها بيانات، إلا بإضافة `--force`.
5. اضبط `DATABASE_URL` في بيئة الخدمة نفسها، ثم شغّلها. في السجل يجب أن يظهر `storage: postgres · schema 002`.
6. ادخل إلى المنصة بحساب معتاد وتأكّد من المشاريع. المستخدمون **لا يحتاجون** إعادة الدخول ما دام `SESSION_SECRET` لم يتغيّر.
7. بعد التأكد صار `data/` قديماً. احتفظ بالنسخة من الخطوة 3 مدة، ثم احذفه.

> ⚠ **لا تفتح المنصة على قاعدة فارغة قبل الخطوة 4.** أول فتح على قاعدة فارغة ينشئ البيانات الأولية (`eyad` / `admin1234`)، وعندها يحتاج الاستيراد `--force`.

## 7. النسخ الاحتياطي والاسترجاع

| المهمة | الطريقة |
|---|---|
| **نسخة كاملة الآن** (مع الحسابات وتجزئات كلمات المرور) | `npm run db:export -- /path/csr-YYYY-MM-DD.json` |
| **نسخة القاعدة كلها** (بما فيها الجداول والترحيلات) | `pg_dump` المعتاد للفريق التقني |
| **نسخ يومية تلقائية** | جدول `csr_backup` (آخر 30 يوماً) |
| **استرجاع من ملف** | أوقف الخدمة ← `npm run db:import -- file.json --force` ← شغّلها |
| **استرجاع يوم من `csr_backup`** | أوقف الخدمة، ثم صدّر نسخة اليوم إلى ملف واستورده بالأمر أدناه. ⚠ **لا تكتب** نسخة اليوم مباشرة في `csr_store.doc`، لأن الحسابات صارت في `csr_users`. |
| **من الواجهة** | قائمة اسم المسؤول ← نسخة احتياطية / استيراد (بلا كلمات المرور) |

أمر استرجاع يوم من `csr_backup`:
```
psql "$DATABASE_URL" -At -c "SELECT json_build_object('rev',1,'doc',doc) FROM csr_backup WHERE day='2026-10-20'" > day.json
npm run db:import -- day.json --force
```
ثم شغّل الخدمة.

**لماذا إيقاف الخدمة؟** الخادم يحمّل البيانات في الذاكرة عند التشغيل، ويكتبها في القاعدة مع أول حفظ. أي تعديل مباشر على القاعدة والخادم يعمل سيُكتب فوقه.

## 8. قواعد العمل على الكود

1. **`npm run check` قبل كل رفع.** يجب أن يطبع `OK 117/117` أو أكثر. يشمل:
   - صياغة الملفات، والملفات الثابتة (ضغط · 304 · تخزين في المتصفح · منع قراءة `server.js` و`db/` و`migrations/`).
   - الدخول، والحفظ، والتعارض، والصلاحيات، وتغيير كلمة المرور، وبقاء البيانات بعد إعادة التشغيل. كل ذلك مرتين: بالملف وبـPostgreSQL.
   - ترحيل قاعدة جديدة، وترحيل قاعدة قديمة من 1.x، ورفض ملف ترحيل معدَّل، و`MIGRATE_ON_START=false`، واستيراد وتصدير مطابقان.
2. **عند تعديل `js/app.js` أو `css/style.css`** ارفع `?v=N` في `index.html` (الآن 13). المتصفحات تخزّن هذين الملفين سنة.
3. **تغييرات القاعدة بملف ترحيل جديد فقط** (القسم 4-ج).
4. **لا تُرجِع التحديث الدائم.** أي طلب دوري في الواجهة يحترم شرط «الصفحة ظاهرة ونشطة» (`IDLE_MS` و`document.hidden` في `boot()`).
5. **كل حفظ يرسل المستند كاملاً.** لا تضع فيه ملفات كبيرة، فهذه تحتاج تخزيناً منفصلاً.
6. **`js/app.js` مكثّف** (أسطر طويلة وأسماء قصيرة). حافظ على أسلوبه، وابحث بأسماء الدوالّ في القسم 9.
7. **UTF-8 ونهايات أسطر LF.** بصمات الترحيلات توحّد نهايات الأسطر، فلا يتأثر الفحص بـCRLF.

### نموذج البيانات (كما يراه الخادم والواجهة)
```
{ v: 7,
  users:    [{ id, login, name, role: 'member'|'manager'|'observer', admin, must, pw }],
  projects: [{ id, name, img, memberId, managerId, sections, steps, ops, stages, links, requests: [{ id, kind, title, msgs, tasks, seen, decision }] }],
  events, seen, perm, committee: { sections } }
```
- **`pw`** لا يخرج من الخادم، فالدالة `strip()` تحذفه قبل الإرسال.
- **صور المشاريع** نص base64 داخل المستند (JPEG بعرض 1000px أقصى)، لذلك حجمه ≈1.4MB اليوم.
- **مرفقات المحادثة** الاسم والحجم فقط.

### الواجهة البرمجية
| الطلب | الوظيفة |
|---|---|
| `GET /api/state` | هل البيانات مهيّأة، ونوع التخزين |
| `POST /api/bootstrap` | أول تشغيل على تخزين فارغ فقط |
| `POST /api/login` | `{login, password}` ← `{token, uid, must}`. الأرقام العربية تُحوَّل، والتجزئة القديمة تُرقّى تلقائياً. |
| `GET /api/data[?rev=N]` | المستند، أو `{same:true}` إن لم يتغيّر |
| `PUT /api/data` | `{rev, data}`. برقم إصدار قديم ← 409 مع الحالي. غير المسؤول لا يغيّر `users` ولا `perm`. |
| `POST /api/password` | تغيير كلمة المرور (6 أحرف على الأقل) |
| `GET /healthz` | فحص الحياة |

### المزامنة في المتصفح (`js/app.js`)
| الدالة | الوظيفة |
|---|---|
| `boot()` | يبدأ الصفحة، ويستعيد الجلسة، ويشغّل مؤقّت التحديث المشروط بالنشاط |
| `pull()` | كل 15 ثانية (بشرط النشاط) أو عند العودة إلى التبويب: `GET /api/data?rev=N` |
| `save()` ← `push()` | يرسل المستند بعد 400ms من أي تعديل. عند 409 يدمج دمجاً ثلاثياً (`merge3()`) ويعيد الإرسال. |
| `writeCache()` · `offerLocalRecovery()` | نسخة أمان في المتصفح، يُعرض استرجاعها على المسؤول إذا عاد الخادم بإصدار أقدم |

> في الكود فرع قديم لـSupabase (`CFG` / `SB` / `rpc()`) **لا يعمل**، لأن `index.html` لا يحمّل `config.js`.
